# Llama 4 Vision Encoder — Implementation Plan

Status: **DONE (structural), 2026-08-15**. `Llama4VisionModel`/`Llama4VisionEncoder`/`Llama4ImagePreprocessor` implemented and passing against the real `mmproj-llama-4-scout-17b-16e-instruct-f16.gguf` (1/1, 0 failures, 132.1s -- one 336x336 tile, 34 blocks, 577 tokens including [CLS]). See the "RESULT" addendum at the end of this doc for what was actually found vs. assumed during implementation.

## Context

After shipping structural (non-parity) CPU implementations of the Gemma 4 E4B (`gemma4v`) and Gemma 3 SigLIP (`gemma3`) ViT encoders, the operator asked which other `llama.cpp/tools/mtmd/models/*.cpp` vision encoders could be built next, scoped to ones whose paired text decoder architecture is realistically usable in this engine.

Four candidates were researched in depth (`llama4`, `qwen2vl`, `qwen3vl`, `glm4v`). Full findings below; the short version:

- **`qwen2vl`, `qwen3vl`, `glm4v` all require genuine multi-axis RoPE ("M-RoPE")** — a 4-axis position scheme fed through `ggml_rope_multi` in the reference implementation. Nothing like this exists anywhere in this engine today: every RoPE call site (CPU `ForwardPass.cs`, CUDA `CudaForwardPass.cs`, Vulkan `GpuForwardPass.cs`, and the vision-side `ApplyRope2DHalf`) takes exactly one scalar position per token. `ModelGraph.cs:500-504` says so explicitly in its own comments. Building any of these three means writing new RoPE kernels on every backend we want it to work on, not just porting a vision tower.
  - `qwen3vl` additionally needs "deepstack" — vision features get added into the *text decoder's* residual stream at several early layers, not spliced once at the embedding layer. No such per-layer injection mechanism exists in any forward-pass loop (`ForwardPass.cs`/`CudaForwardPass.cs`/`GpuForwardPass.cs`/`HybridForwardPass.cs`); the only related mechanism (`EnableHiddenTaps`) is read-only, the wrong direction. This is the most invasive of the four candidates.
  - `glm4v` is the least-bad of the three M-RoPE candidates because its text decoder (`glm4`) is already admitted in its non-multimodal mode, and the RoPE call site it would extend (`ForwardPass.cs:3106-3114`) is already a clean, generic dispatch point — but the M-RoPE kernel itself still doesn't exist and would still need writing.
- **`llama4`** is the only candidate whose text decoder (`llama4`) is already fully admitted and working, and it needs **no new RoPE kernel type** — it uses a 2D half-RoPE (X/Y axes) plus a learned absolute position table, both added simultaneously. This is the same *shape* of mechanism as `Gemma4VVisionEncoder.ApplyRope2DHalf`, just called on top of a learned-table add rather than instead of one. Its real new-ness is entirely on the vision-encoder side: a CLS token, a pixel-shuffle merger, and — most significantly — llama.cpp's own multi-tile "llava-uhd" preprocessing (an image gets tiled into up to a 3x3 grid of square tiles plus one downsampled "overview" tile, each run through the ViT independently).

None of the four is a small job. But `llama4` is the only one that stays entirely within "port a vision tower using patterns we already have," rather than requiring new cross-backend engine machinery (M-RoPE kernels) or invasive changes to the main text-decoder forward loop (deepstack). It also doesn't foreclose the other three — writing an M-RoPE kernel is a legitimate future project, just a much bigger one than "one more encoder."

**Decision: build `llama4` next**, scoped the same way `gemma4v`/`gemma3` were: a structurally-verified, isolated ViT forward pass (loader + encoder + preprocessor + sanity test), with two things explicitly deferred, matching the existing precedent for the other two encoders:

- **Multi-tile orchestration is out of scope for this phase.** The per-tile ViT forward pass (one `image_size × image_size` square in, embeddings out) is what gets built and tested. Deciding how many tiles a given source image needs, slicing it, and interleaving tile-boundary tokens in the prompt is prompt-builder/engine-level work, tracked separately, not blocking a first structural build of the encoder itself.
- **Decoder splice (Phase V4) is out of scope**, exactly as it already is for `gemma4v`/`gemma3`. `Gemma4VVisionModel.cs`'s own doc comment states this precedent explicitly: *"It does not claim that encoder forward, token reduction, or image-token mask semantics are implemented; those must be parity-derived before embeddings are admitted to the text decoder."* Same rule applies here. (Note for later: `ForwardEmbedding`/`SplicePrefillImages` in `InferenceEngine.cs` is real and working, but only for the older encoder-free `gemma4uv` projector — none of the three ViT encoders, `gemma4v`/`gemma3`/`llama4`, are wired into it yet.)
- **Known quality caveat, worth remembering**: llama.cpp's own code carries a runtime warning for this exact projector (`mtmd.cpp`: *"llama 4 vision is known to have degraded quality"*, linking ggml-org/llama.cpp#13282). Even a perfect port inherits that ceiling — flagging so it isn't mistaken for an implementation bug later if downstream numbers look mediocre once parity testing eventually happens.

## Architecture summary (`llama4`, from `tools/mtmd/models/llama4.cpp` + shared `clip.cpp` helpers)

- **Projector type string**: `PROJECTOR_TYPE_LLAMA4`, GGUF key value `"llama4"`.
- **Patch embed**: `Llama4UnfoldConvolution` — im2col + matmul (not raw `ggml_conv_2d`), `[patch_size, patch_size, 3] -> n_embd` kernel. A **CLS token** is concatenated after patch embedding (`ggml_concat(inp, class_embedding, dim=1)`) — neither `gemma4v` nor `gemma3` has one, this is new.
- **Position embedding — two mechanisms simultaneously** (this is the reusable-pattern reason `llama4` is tractable):
  1. A **learned absolute position-embedding table**, added once before the block loop (inside `build_vit`), same shape of mechanism as `gemma3`'s single-lookup position table.
  2. **2D half-RoPE** on Q/K inside every block (`build_rope_2d`): first half of head-dim rotated by X (column) position, second half by Y (row) position, NEOX-style pairing. This is functionally the same pattern already implemented as `Gemma4VVisionEncoder.ApplyRope2DHalf` — reusable as-is, just needs to run alongside the position-table add rather than as an alternative to it.
- **Normalization**: LayerNorm (not RMS) throughout, pre-norm only (no sandwich post-norms), no QK-norm.
- **Attention**: standard scaled dot-product, `1/sqrt(headDim)`, full bidirectional over `n_patches + 1` (CLS included). No windowing.
- **FFN**: gated, activation per GGUF `clip.use_gelu`/`use_silu` metadata (check at load time, same pattern as the `gemma4v`/`gemma3` loaders already use).
- **No clamp mechanism** (`clamp_info_map` is `gemma4v`/`gemma4uv`-specific; `llama4` doesn't override `build_mm`).
- **Merger/projector tail — new pattern, not reused from either existing encoder**:
  1. **Pixel-shuffle** (space-to-depth) reshape: groups `scale_factor × scale_factor` adjacent patches into one wide vector along the embedding axis (`n_embd * scale_factor²`), reducing token count by `scale_factor²`. `scale_factor` = `n_merge`, read from GGUF `clip.vision.projector.scale_factor` (falls back to whatever the loader treats as unset if absent — verify against the real checkpoint's metadata once downloaded, same as the `clip.projector_type` vs `clip.vision.projector_type` naming surprise found for `gemma3`).
  2. A 2-layer GELU MLP, no bias (`Llama4VisionMLP2`).
  3. A final linear projector (`Llama4MultiModalProjector`) into LLM embedding space — verify at load time whether this tensor is stored transposed like `mm.input_projection` was for both `gemma4v` and `gemma3` (both needed a materialized transpose; assume the same until proven otherwise).
- **CLS token handling in the output**: verify from the real tensor shapes/metadata whether the CLS token row survives into the merger input or gets dropped before pixel-shuffle — `llama4.cpp`'s merger reshape assumes `n_patches_x == n_patches_y` (square grid), so this needs checking directly against the C++ source at implementation time, not assumed from this summary.

## Files to add (mirrors the `Gemma3Vision*`/`Gemma4VVision*` pattern exactly)

- `src/OpenTail.Stingray.Vision/Llama4VisionModel.cs` — GGUF loader. Hand-rolled `Open(string mmprojPath)` factory, same shape as `Gemma3VisionModel.cs`/`Gemma4VVisionModel.cs` (no shared base class exists in this codebase for vision loaders — each is independent, copy-and-adapt is the established pattern). Validate hard, fail loud on any unexpected tensor name/shape, per both existing loaders' documented philosophy.
- `src/OpenTail.Stingray.Vision/Llama4VisionEncoder.cs` — forward pass: patch embed + CLS concat → learned pos table add → N blocks (LayerNorm → QKV → 2D half-RoPE via the existing `ApplyRope2DHalf` helper → attention → out-proj → residual → LayerNorm → gated FFN → residual) → pixel-shuffle merge → 2-layer GELU MLP → linear projector. Use `Parallel.For` across patches/heads from the start (not sequential-then-optimize like the `gemma3` build) — that back-and-forth cost real time last round and the pattern is now known upfront.
- `src/OpenTail.Stingray.Vision/Llama4ImagePreprocessor.cs` — single-tile, fixed-square preprocessing (`image_size × image_size`), reusing `Gemma4VImagePreprocessor.ResizeNormalize` the same way `Gemma3ImagePreprocessor.cs` does (thin wrapper, different mean/std/size). Multi-tile slicing explicitly NOT built this phase (see Context).
- `tests/OpenTail.Stingray.Tests.Vision/VisionTestPaths.cs` — add `Llama4MmprojFile` constant + `FindLlama4Mmproj()`, same pattern as the existing `Find*()` methods.
- `tests/OpenTail.Stingray.Tests.Vision/Llama4VisionEncoderTests.cs` — structural sanity test only (shape, no NaN/Inf, non-degenerate magnitude, pinned geometry constants), explicitly labelled as such in a doc comment, same as `Gemma3VisionEncoderTests.cs`/`Gemma4VVisionEncoderTests.cs`. No numerical-parity oracle exists locally, same caveat as before.

## RESULT — 2026-08-15

Implemented and passing. The real checkpoint (Scout, `clip.vision.block_count=34`, `embedding_length=1408`, `head_count=16` -> head_dim 88, `feed_forward_length=5632`, `image_size=336`, `patch_size=14` -> 24x24=576 patches, `scale_factor=2` -> 144 output soft tokens, `projection_dim=5120`) differed from this doc's pre-implementation assumptions in several concrete, verified ways -- all found by loading the real file and fixing forward from real errors, same process as the Gemma 3 build:

- **Metadata key**: `clip.projector_type` (no `.vision.` segment) -- same surprise as `gemma3`'s mmproj, NOT the `clip.vision.projector_type` convention `gemma4v`/`gemma4uv` use. Third data point now for "don't assume the convention transfers between exports."
- **`v.patch_embd.weight`** is a flat 2D `[588, 1408]` **Float16** matrix, not the 4D `[14,14,3,1408]` **Float32** shape both other encoders use. `Llama4UnfoldConvolution` reshapes it to 4D in-graph for im2col; the on-disk/loaded shape is flat.
- **No FFN gate tensor at all** (`v.blk.N.ffn_gate.weight` absent for every block) -- the per-block FFN is plain `down(act(up(x)))`, not gated, despite `llama4.cpp`'s generic `build_ffn` call being able to support gating if the tensor were present. `clip.use_gelu=true`, so activation is plain tanh-GELU (not quick-GELU, and not silu).
- **Real `v.pre_ln`/`v.post_ln`** (weight+bias, both present) -- unlike `gemma4v` (neither) and `gemma3` (post_ln only, no pre_ln). Both apply once, to all 577 tokens (576 patches + [CLS]), around the 34-block loop.
- **2D-RoPE pairing convention is NORM/interleaved, not NEOX** -- confirmed directly from `clip.cpp`: `llama4.cpp` calls the shared `build_rope_2d` helper as-is, whose inner `ggml_rope_ext` calls use mode 0 (interleaved consecutive pairs), while `gemma4v.cpp` hand-rolls its own rope function specifically commented "similar to build_rope_2d, but use neox ordering." This meant `Gemma4VVisionEncoder.ApplyRope2DHalf` could NOT be reused as-is -- a new `Llama4VisionEncoder.ApplyRope2DHalfNorm` was written with interleaved-pair rotation instead of split-half rotation. Would have been a silent correctness bug (wrong rotation, no crash) if not caught by reading `clip.cpp` directly before implementing rather than assuming the existing helper transferred.
- **No storage-transpose anywhere** -- unlike `gemma3`'s `mm.input_projection`, none of `llama4`'s merger tensors (`mm.model.mlp.1/2.weight`, `mm.model.fc.weight`) needed a transpose; `llama4.cpp` never calls `ggml_transpose`, and all three loaded with the ordinary row-major `[input,output]` convention. Their intermediate widths (mlp hidden 4096, mlp2 output 4096) aren't declared by any metadata key -- validated by chaining each tensor's own on-disk shape into the next rather than asserting a hardcoded expected value; the final chained output width (5120) matched the independently-present `clip.vision.projection_dim` metadata as a cross-check.
- **Pixel-shuffle merger channel layout** was derived by hand from `llama4.cpp`'s `reshape/permute/reshape` sequence (not available as a simple average like `gemma3`'s pooling): merged feature index `dy*embd*NMerge + dx*embd + c` sourced from patch `(row=yg*NMerge+dy, col=xg*NMerge+dx)`, output token index `yg*(grid/NMerge)+xg` -- implemented as an explicit nested loop, no shortcuts.
- **Performance**: 132.1s fully parallelized (`Parallel.For` across tokens for QKV/output/FFN, across heads for attention) on the first attempt -- no separate sequential-then-parallelize pass was needed this time, unlike `gemma3` (which cost real iteration time going from ~35min single-threaded to 562s). Substantially cheaper than `gemma3`'s 562.5s despite similar block count (34 vs 27), because the token count is far smaller (577 vs 4096) -- attention cost scales with the square of token count.

Same caveats as `gemma4v`/`gemma3` apply: structural sanity only, no numerical parity oracle exists locally, and Phase-V4-equivalent decoder splice + multi-tile orchestration are both explicitly out of scope for this phase. Additionally, llama.cpp's own code carries a runtime warning that this exact projector is known to have degraded quality (ggml-org/llama.cpp#13282) -- a ceiling independent of whether this port is numerically correct.
