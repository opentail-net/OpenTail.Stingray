# Plan 6 (2026-11-01): what plan 5 left, and the product-side gaps found while checking it

Written when [plan 5](2026-11-01-plan-5.md) ran out of items that need neither a quiet machine, a download, an owner decision nor hardware this machine lacks. Source: plan 5's own leftovers, plus the product-side documents plan 5 did not take (the multi-model runtime plan, known-good checkpoints, the public developer surface, samples). The rule from plans 4 and 5 stands: a box is kept only if it names a failure, a user-visible limitation, a measurable gain or a recurring cost, can be verified on this machine, and was **checked against the code first**; each box below says how. Rules in force: no subagents; never `git add -A`; `Tests.Core` before merging; mutation-check new tests (confirm with `git diff --stat` that the mutation changed the file); timed real-weight runs; perf only on a quiet machine, interleaved, 3+ runs; rule 13 (an iGPU result says nothing about a discrete GPU); one merged PR per item.

Contracts this must satisfy: the CI floors in `.github/workflows/ci.yml`; `StatusMatrixCitationTests` and `DocumentationLinkTests`; STATUS rows are sourced (rule 10); "ported, not verified" families stay internal (rule 14); `CatalogGuardTests` (every catalog entry's hash, revision, evidence and cited golden).

## Checklist

### A. Documents that contradict the code

- [ ] **A1** The known-good-checkpoints plan says "P0 leftover: `pull`'s download and listing parser still use their own client and parser" (its checklist line 7, its status line, and its open-items list line 193), and `reference/061-coverage-tooling.md` line 28 says `pull`'s file download is "still on its own client, not yet routed through the gateway". *Checked 2026-11-01:*
  `PullCommand.DownloadWithResume` calls `ModelDownloader.DownloadAsync`, the same code `setup` uses; the listing goes through `Core.Net.ExternalHttpClient` (`PullCommand.cs` line 171); and the download client is `ModelDownloader.CreateClient` (line 61: Hugging Face hosts only, redirects checked, token to the Hub only, via `HuggingFaceOnlyHandler`). So the "own parser" half is done. One honest residual: large downloads use that handler,
  not `ExternalHttpClient` itself (no timeout, streamed), with the same host rule; whether that is intended and should be stated in 061 is a one-line decision for the PR. The same plan's "P5 docs as tests" is mostly met: `CatalogGuardTests` pins every entry's hash, revision, size and evidence (`EveryEntry_Files_HaveValidSha256RevisionSizeAndRepoPath`, `EveryEntry_HasNonEmptyEvidence`) and that each qualification cites a golden that exists and pins the same file
  (`EveryQualification_CitesAGoldenThatPinsTheSameFile`); `StatusMatrixCitationTests` covers STATUS. What is not covered is README commands being run, which item B1 starts. Done when the four places say so, one line each in the PR.
### B. A continuous-integration gap

- [ ] **B1** Nothing in CI builds the samples or the README snippets against the packed package. *Checked 2026-11-01:* `scripts/verify-package-consumers.ps1` (packs both packages into a throw-away feed, builds every README block marked `<!-- verify:consumer -->` and the samples that claim to be consumers: Chat, Extract, Speech, Diffusion, ChatServer) is
  referenced by docs and `scripts/README.md` and by no workflow; `ci.yml` and `release.yml` run `verify-nuget-package.ps1`, which does not mention samples. `OpenTail.Stingray.slnx` lists three of the eight folders under `samples/` (Chat, HotRouting, ToolCall), so Extract, Speech, Diffusion, ChatServer and QuickStart are built by nothing, and can rot while every
  check stays green. Do: (1) run the script locally and record its duration and result; (2) add a step to the Windows job after the pack step, passing `-Feed` and `-Version` of the packages already built so it does not pack twice; (3) decide for QuickStart and HotRouting/ToolCall whether they belong to the script's list. Done when CI builds all eight sample folders and the
  snippets, and a deliberately broken snippet (a mutation, confirmed to change the file) fails the step locally.

### C. Multi-model runtime (`032` plan, Phase 3)

- [ ] **C1** Accelerator-aware admission is never fed in the shipped server. *Checked 2026-11-01:* `ModelRuntimeManager` threads `CandidateAcceleratorBytes` into `IResourceBudget.EstimateAdmission` and the budget (`HostResourceBudget`) compares it with known device capacity, but the manager's constructor takes the estimator as an optional delegate that defaults to
  `_ => 0` (its own comment says so), and the only production construction, `ServiceCollectionExtensions.cs:80`, passes neither estimator. So with `EnableResourceAdmission` on, every candidate counts as 0 accelerator bytes and the accelerator branch (and its tests, which pass a fake delegate) never runs in a real server. The plan's open item "hybrid-GDN full-offload accounting"
  presupposes an estimator exists. *Not yet checked:* what the loader can know before loading (`ExecutionPlanner.Plan` is pure and gives `EstimatedVramMb`; whether it can be run per candidate without loading). Do: read that, write the design in the PR (an estimator from the static plan, or a documented decision that admission is host-memory only), then implement it with a test
  that a candidate larger than the fake device capacity is refused through the real DI wiring. Done when `032` says which it is.
