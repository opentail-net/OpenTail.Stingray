10. How is this actually achieved?
There are several architectures.
Architecture 1 — separate processes
The simplest:
Process 1
llama-server Qwen

Process 2
llama-server Gemma

Process 3
llama-server LFM
Each owns its own model.
OpenTail talks to all three.
Advantages
Very easy.
Disadvantages
You duplicate:
runtime state
memory management
scheduling
potentially model weights
CPU resources
And there's no central understanding of the machine's total inference workload.
11. Architecture 2 — one server, multiple model instances
This is becoming more common.
Interestingly, current llama.cpp already supports this.
Its server can run in router mode, dynamically loading/unloading models and routing requests to the appropriate model instance. Its current router supports a configurable maximum number of simultaneously loaded models; the documented default is four. GitHub
Conceptually:
                 llama-server
                      │
               ┌──────┼──────┐
               ↓      ↓      ↓
            Model A Model B Model C
So this is not something you would need to invent from scratch if Stingray is using llama.cpp-style infrastructure.
12. Ollama already does this too
Ollama explicitly supports multiple models being loaded concurrently if sufficient memory is available.
Its documentation describes:
multiple models loaded simultaneously
configurable maximum loaded models
parallel requests per model
queuing when memory isn't sufficient
automatic unloading of idle models
For CPU inference, the constraint is system memory; for GPU inference, the models need to fit in available VRAM for concurrent loads. Ollama
So:
"Can Ollama run multiple local LLMs?"
Yes.
"Can it automatically manage which models stay resident?"
Yes.
"Can multiple models actually infer concurrently?"
Yes, when the hardware has enough memory/resources.
13. There's another distinction: multiple models vs multiple adapters
This is worth knowing because it can save enormous memory.
Suppose you have:
Llama 3 8B
       │
 ┌─────┼─────┐
 ↓     ↓     ↓

14. What about GPUs?
There's an important distinction between:
one model across multiple GPUs

For example:

   ├── GPU 0

That's multi-GPU model parallelism, not multiple-model inference.

15. The really interesting architecture for Stingray
I'd actually separate the concepts.
I wouldn't make:
Stingray = one model

the fundamental abstraction.
I'd make:
Stingray = inference runtime capable of managing many model instances.

Something like:
                    OpenTail
                       │
                Inference Manager
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ↓              ↓              ↓
   Model Instance  Model Instance  Model Instance
        │              │              │
      Qwen           Gemma           LFM
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                Resource Scheduler
                       │
              ┌────────┴────────┐
              ↓                 ↓
             CPU              GPU
              │                 │
           RAM/KV          VRAM/KV
Then you can add policies such as:
Residency
Keep Gemma loaded because it's used frequently.

Eviction

Priority
User-facing Qwen request gets priority over background summarisation.

Resource limits
Don't allow more than 28 GB of model/KV memory.

Admission control
Don't start another model if doing so will cause swapping.

Scheduling
Run the small classifier alongside the large model, but don't allow it to starve the main request.

LEVEL 1

Multiple sessions concurrently
        ↓

Multiple different models resident
        ↓

Levels 1–3 are largely solved technology.

That gives you the flexibility later to do routing, parallel workers, model committees, background AI and specialist models without having to redesign Stingray's core.

Plan 032 — Multi-Model Inference Runtime, Residency & Scheduling
Status
Implementation-ready design.
This plan supersedes the shelved production portion of 024-multi-model-serving-and-request-scheduling-plan.md.
It does not simply revive 024 unchanged.
The intended deployment model has now been clarified:
OpenTail is a multiuser local AI service, not merely a single-user CLI.
The normal deployment will likely have one or two resident models.
A small/medium model can act as the persistent sidekick, tool caller and orchestrator.
A larger model can be brought in as a specialist/deep-reasoning model.
Two models may genuinely generate simultaneously when hardware permits.
Multiple users may generate against the same model simultaneously.
Stingray must support N model instances architecturally, without assuming that N is large.
Residency should be resource/memory-pressure driven, not an arbitrary fixed model count.
On constrained machines, Stingray must naturally degrade to single-slot operation.
The expected sweet spot is 1–2 resident models, not a large model farm.
The earlier 025/026 work remains useful as groundwork: reference-counted model sharing and bounded eviction are exactly the lower-level mechanisms needed here. The previous Phase 2 plan deliberately stopped short of scheduling and session awareness. 026-shared-model-cache-phase2-eviction-plan.mdMD
1. Problem this plan solves
Stingray currently has strong machinery for:
model execution;
HotSession lifecycle;
paged KV;
concurrent decode;
continuous batching;
KV memory governance;
prefix sharing;
session branching;
model coverage.
The missing abstraction is above those pieces:
There is no first-class concept of several independently loaded model runtimes sharing one Stingray process and competing for finite machine resources.

The old 024 identified the underlying problem correctly, but deliberately treated concurrent execution of multiple models as a future concern.
That assumption is no longer appropriate for OpenTail.
A realistic OpenTail deployment can look like:
                    OpenTail
                       │
             ┌─────────┴──────────┐
             │                    │
          Sidekick             Reasoner
           8B-ish                20–30B
             │                    │
       Users A/B/C             User D
At another moment:
Sidekick + Reasoner resident
          │
          ├── User A → Sidekick
          ├── User B → Sidekick
          └── User C → Reasoner
And on a smaller machine:
Sidekick resident

Reasoner requested
       ↓
memory pressure
       ↓
Sidekick suspended/evicted if safe
       ↓
Reasoner runs
The runtime therefore needs to solve three related but distinct problems:
Model residency — which complete models are loaded?
Resource admission — can another model/session safely run?
Inference scheduling — which sessions/models receive compute?
These should be separate concerns.
2. Design principles
2.1 N is a capability, not the expected deployment size
Do not design around:
MaxModels = 2;
Instead:
Model instances = N
with resource policy determining how many can actually remain resident.
A 16 GB machine may operate as:
1 resident model
A 64 GB machine might naturally operate as:
2 resident models
A larger workstation might support:
3+
without changing the architecture.
2.2 Model count is not the resource budget
Do not equate:
2 models = safe
because:
models have radically different sizes;
KV requirements differ;
sessions differ;
batch sizes differ;
CPU and memory bandwidth matter;
accelerator memory may be independent of host RAM.
The admission decision must therefore be resource-based.
2.3 Same-model concurrency is the common case
Ten users requesting the sidekick should not mean ten copies of the model.
Instead:
                  Sidekick
                     │
              continuous batch
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
     Session A    Session B    Session C
       KV A          KV B          KV C
The existing continuous-batching and KV/session architecture remains responsible for this.
Multi-model scheduling must sit above it.
2.4 Different-model concurrency is allowed
If:
Sidekick
Reasoner
are both resident and resources permit, both may have active work.
There is no global "only one model may generate" lock.
Instead:
ModelRuntime A
     │
     └── batch A

ModelRuntime B
     │
     └── batch B
can progress concurrently.
The runtime scheduler controls resource fairness rather than serialising unrelated models unnecessarily.
3. New core abstraction: ModelRuntime
The fundamental unit becomes a complete independently executable model runtime.
Conceptually:
public sealed class ModelRuntime : IDisposable
{
    public ModelId Id { get; }

    public GgufModel Model { get; }

    public IInferenceEngine Engine { get; }

    public long EstimatedModelBytes { get; }

    public ModelRuntimeState State { get; }

    public int ActiveRequests { get; }

    public int ActiveSessions { get; }

    public bool IsPinned { get; }
}
Possible states:
public enum ModelRuntimeState
{
    Unloaded,
    Loading,
    Ready,
    Active,
    Draining,
    Evicting,
    Failed,
    Disposed
}
The exact implementation should follow existing Stingray conventions rather than blindly reproducing this sketch.
Important invariant
A runtime may only be evicted when:
State permits eviction
AND
ActiveRequests == 0
AND
ActiveSessions == 0
AND
not pinned
A model being "least recently used" is not sufficient to make it evictable.
4. ModelRuntimeManager
Introduce a production model-runtime manager.
Conceptually:
public interface IModelRuntimeManager
{
    ValueTask<ModelRuntimeHandle> AcquireAsync(
        ModelId model,
        CancellationToken cancellationToken = default);

    bool TryGetResident(
        ModelId model,
        out ModelRuntime runtime);

The manager owns:
model lookup;
canonical identity;
loading;
single-flight loading;
residency;
reference/lifetime tracking;
eviction;
runtime disposal.
It should build on the already-proven SharedModelCache concepts rather than creating a second unrelated ownership system.
The existing cache is currently process-wide and reference-counted by canonical model path. 
5. Single-flight model loading
This is mandatory.
If five users simultaneously request a cold model:
User A ─┐
User B ─┤
User C ─┼──> Model X
User D ─┤
User E ─┘

             one physical load
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
          A        B        C
not:
five × GgufModel.Open()
Use:
Dictionary<ModelId, Task<ModelRuntime>>
or an equivalent existing async single-flight primitive.
All callers await the same load.
6. Residency states
A model's lifecycle must distinguish physical residency from active use.
Recommended conceptual states:
UNLOADED
   │
   ▼
LOADING
   │
   ▼
READY
   │
   ▼
ACTIVE
   │
   ▼
READY
   │
   ▼
EVICTING
   │
   ▼
UNLOADED
A runtime can therefore be:
Resident + idle
Loaded but doing nothing.
Resident + active
Serving one or more sessions.
Loading
Not yet available for inference.
Draining
No new work accepted; existing work is completing.
Evicting
Guaranteed no active references remain; physical resources being released.
7. Resource admission
The old 024's IResourceBudget idea should be retained, but simplified and made concrete.
The key abstraction is:
public interface IResourceBudget
{
    ResourceSnapshot GetCurrent();

    ResourceAvailability EstimateAdmission(
        ModelRuntimeSpec model,
        InferenceWorkEstimate work);

The exact API can be adjusted to existing resource abstractions.
At minimum, distinguish:

Model residency
KV memory
Do not collapse these into one number.
For example:

KV requires:          4 GB RAM
may be admissible.
Whereas:
RAM available:       40 GB
VRAM available:       1 GB
Model requires:       8 GB VRAM
is not.
8. Memory pressure is the residency policy
Do not use:
MaximumResidentModels = 2
as the primary policy.
Instead:
                    New model request
                           │
                           ▼
                   Resource admission
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
           Allowed     Evictable      Reject /
                        model exists    wait
              │            │
              │            ▼
              │         evict it
              │            │
              └────────────┘
                     │
                     ▼
                 load model
A configurable soft residency target may still be useful, but it is subordinate to actual resource pressure.
9. Single-slot mode
This is an explicit supported operating mode, but should not require a different architecture.
On a constrained machine:
Model A resident
Request Model B:
Model A
   │
   ├── no active work
   └── evict
        ↓
Model B
If Model A has live users:
Model A
   │
   └── active
       ↓
Model B requested
       ↓
cannot safely evict
       ↓
queue Model B
Do not kill active inference simply to satisfy residency.
This gives the desired behaviour:
small machine = naturally single-slot; larger machine = naturally multi-model.

10. Concurrent model execution
This is the major change from 024.
If:
Model A = resident + active
Model B = resident + active
Stingray must permit:
A → inference
B → inference
to overlap.
There must be no process-wide:
lock (_inferenceEngine)
or equivalent architectural bottleneck.
Each ModelRuntime owns its own execution state.
11. Scheduling hierarchy
Scheduling should occur at two levels.
Level 1 — model runtime
Which model runtimes are eligible to execute?
Sidekick
Reasoner
Vision
Level 2 — session/batch
Which sessions within that model are included in its next decode batch?
Sidekick
 ├── User A
 ├── User B
 └── User C
The second level remains the responsibility of the existing continuous-batching machinery.
Do not duplicate token scheduling in the multi-model scheduler.
12. Model scheduling policy
The initial cross-model policy should be deliberately simple.
Each runtime exposes:
public readonly record struct ModelSchedulingInfo(
    ModelId ModelId,
    int PendingRequests,
    int ActiveRequests,
    int ActiveSessions,
    bool IsResident,
    bool IsPinned,
    TimeSpan OldestRequestAge,
    TimeSpan EstimatedLoadCost);
The scheduler uses this information to determine whether a model should receive execution time.
Initial policy:
never starve a model indefinitely;
favour already-resident models;
favour interactive work;
respect request age;
respect resource limits;
don't evict an actively useful model merely to save a small amount of memory;
don't allow a busy model to monopolise all execution capacity.
Do not build a complex optimisation/scoring engine initially.
The stable ModelSchedulingInfo seam is more important than the first scoring formula.
13. Service quantum
Retain the useful idea from 024:
A continuously busy model should not necessarily consume all available execution indefinitely.
Conceptually:
Model A
████████████████
       quantum
          ↓
Model B
██████
But unlike 024, this is not a reason to serialise models that can genuinely execute concurrently.
The quantum applies when the underlying resource is contended.
If CPU/GPU resources are sufficiently available:
A ────────────────
B ────────────────
can run concurrently.
If resources are saturated:
A ──────┐
        ├── scheduler
B ──────┘
the scheduler applies fairness.
14. Session/model affinity
A HotSession must have an immutable model identity.
Conceptually:
HotSession
   │
   └── ModelId
A session cannot silently move:
Model A → Model B
because its KV state, tokenizer assumptions, architecture and runtime state are model-specific.
If a request asks for another model, OpenTail must create/use another session.
15. Model eviction and live sessions
This remains a hard correctness rule from 024.
Never:
LRU says Model A is cold
        ↓
dispose Model A
        ↓
discover Session A still owns KV/state
Instead:
Model A
 │
 ├── active requests
 ├── live sessions
 └── KV/session state
        ↓
      pinned
        ↓
    not evictable
When the final model/session reference disappears:
ActiveRequests = 0
ActiveSessions = 0
the runtime becomes eligible.
16. KV memory and model residency are separate
The existing KV memory governor must remain responsible for KV pressure.
The new model residency manager is responsible for whole-model pressure.
Conceptually:
             Stingray resources
                    │
        ┌───────────┴───────────┐
        ↓                       ↓
   Model residency          KV residency
        │                       │
 Model eviction          Session suspension
        │                       │
        └───────────┬───────────┘
                    ↓
             Resource budget
Do not make the model manager reach into KV internals.
Do not make the KV cache know about models.
This separation is particularly important because the existing KV governor already has well-defined suspension semantics and must not directly release physical pages. 
17. Eviction hierarchy
When memory pressure occurs, prefer reclamation in this order:
1. Unused model runtime
2. Idle/evictable model runtime
3. Model runtime whose active sessions can safely be drained
4. KV/session suspension
5. Queue/admission
6. Hard failure
However, do not automatically combine these mechanisms in Phase 1.
The first implementation should establish explicit ownership:
model manager → model residency;
KV governor → KV residency;
scheduler → execution;
session → session correctness.
A later policy layer can coordinate them.
18. Request admission
A request must not disappear into an unbounded queue.
When a model is:
resident + runnable
execute it.
When:
loading
join the single-flight load.
When:
resident but resource constrained
queue subject to scheduler policy.
When:
cannot ever be admitted
return a deterministic resource error.
The API must distinguish:
queued
loading
running
completed
cancelled
rejected
19. Cancellation
Cancellation must propagate through:
request
  ↓
scheduler
  ↓
model runtime
  ↓
session
  ↓
generation
If the last waiting request for a cold model is cancelled before loading begins, Stingray should be allowed to cancel the load if safe.
If another request is waiting on the same single-flight load:
A cancels
B remains

The cancellation belongs to the caller, not the shared load.
20. Model loading failure
A failed load must not poison the model registry indefinitely.
For:
Model A → Loading → Failed
waiting requests receive the same failure.
Subsequent requests may retry according to a bounded retry/backoff policy.
Do not leave:

permanently faulted in the single-flight dictionary.

31. Performance acceptance
Do not judge this feature purely by aggregate tokens/sec.
Measure:
Scenario	Important metric
One model / one user	baseline latency
One model / many users	throughput + fairness
Two models / one user each	overlap
Two models / many users	throughput + latency
Cold second model	load penalty
Memory-pressure eviction	recovery time
Repeated model switching	physical load count


The desired result is not:
"Always run two models."

It is:
"When two models fit, running them concurrently should be materially better than repeatedly swapping them."

32. Critical invariants
These should be written into tests and code comments.
Invariant 1
A model runtime is disposed exactly once.
Invariant 2
A runtime with active requests or sessions cannot be evicted.
Invariant 3
Concurrent acquisition of one cold model produces one physical load.
Invariant 4
One session belongs to exactly one model runtime.
Invariant 5
One model runtime may serve many sessions concurrently.
Invariant 6
Different model runtimes may execute concurrently.
Invariant 7
Resource admission never relies solely on model count.
Invariant 8
KV memory ownership remains with the KV/session subsystem.
Invariant 9
Cancellation of one request cannot cancel shared work needed by another request.
Invariant 10
When resources are insufficient, Stingray queues or rejects work safely; it never violates runtime/session ownership to make room.

This is where I think the new plan is materially better.
I would not resurrect the old architecture wholesale.
In particular, don't build:

The old 024 correctly identified several hard problems, including live-session eviction and synchronous 20–50 GB loading, but it also deliberately excluded concurrent multi-model execution.

That is much less speculative.
34. Final architecture
The resulting shape is:
                         OpenTail
                            │
                            ▼
                    IInferenceService
                            │
                    ┌───────┴───────┐
                    │               │
                 Model A          Model B
                 Sidekick         Reasoner
                    │               │
             ┌──────┴──────┐  ┌─────┴─────┐
             │             │  │           │
           HotSession    HotSession    HotSession
             │             │              │
             └──────┬──────┘              │
                    ▼                     ▼
             Continuous Batch       Continuous Batch
                    │                     │
                    └─────────┬───────────┘
                              ▼
                     Model Scheduler
                              │
                     Resource Admission
                              │
                ┌─────────────┴─────────────┐
                ▼                           ▼
          Model Residency              KV Governor
                │                           │
                ▼                           ▼
           Model Cache                  KV Cache
And the key point is:
The scheduler doesn't own the models, the model cache doesn't own sessions, and the KV governor doesn't own models.

Each subsystem has one job.
My recommendation
I think this is the plan I would now use instead of 024.
The previous 025/026 work was not wasted — it established the ownership and eviction mechanics we need. The scope decision was also reasonable at the time, because the repository explicitly had no demonstrated production multi-model requirement. 027-model-cache-scope-decision.mdMD
But with the OpenTail requirement now being:
cheap persistent sidekick + on-demand deep model + multiuser + genuine concurrent generation where hardware permits

the old decision has become obsolete.
The particularly important design choice is not "support two models." It's:
Make model instances first-class resources, and let memory/resource pressure determine whether the machine behaves as a one-model, two-model, or N-model system.

That gives us the reality you expect — probably two — without baking "two" into Stingray, and without accidentally turning the project into a miniature vLLM clone. The current repo's stated direction is already centred on broad GGUF coverage and the newer HotSession architecture, so this plan should sit above those rather than compete with them.
