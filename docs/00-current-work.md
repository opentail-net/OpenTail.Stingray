##### A5. Device memory figure understates real use

- **Why:** on a Ryzen 7 5700G (Vulkan, every layer offloaded, context 512), dense Qwen3-0.6B Q8_0 held 1152.7 MiB device-local against a planned figure of 761.8 MiB. Hybrid-GDN Qwen3.5-0.8B Q8_0 held 1612.2 MiB against 827.8 MiB. The ledger matched the OS counters within 1% (`scripts/gpu-process-memory.ps1` reads the OS counters).
- **Causes, confirmed in the code:**
  1. The planner counted a Q8_0 input embedding as packed bytes, but both Vulkan embedding lookup paths expand Q8_0 to F32. The output table uses the ordinary raw-quant matvec path and remains packed. This explains a substantial part of the dense Qwen3-0.6B undercount.
  2. `ModelDescription.MeasureLayerGpuBytes`'s old fixed tensor list omitted hybrid GDN projections (195.3 MiB for Qwen3.5-0.8B); the family-specific tensor list is now included.
  3. The old device-local ledger includes more than static weights: KV cache, recurrent state, scratch, driver allocations and possibly transient staging. A static weight estimate cannot be compared to that total within 5% without defining and measuring the same allocation categories.

##### A15. Single-slot admits a second model while the first is still loading (verified 2026-11-24)

##### A28. A prompt longer than the context window is a 500, not a 400 (verified by reading 2026-11-24; fixed 2026-11-24)

- **Why:** the server never checks a prompt's token count against the model's context length. The engine reserves KV space clamped to `MaxSeqLen` (`src/OpenTail.Stingray.Engine/ContinuousBatchingEngine.cs` around line 1012), and the forward pass throws `ArgumentOutOfRangeException` at the first position past the context (`ForwardPass.BatchedIO.cs` around lines 70-76: "Position exceeds the active context length"). ##### A29. Ordinary generation is not stopped at the context window, so decode can run past it (HIGH, possible memory corruption; fixed 2026-11-24, evidence below)

- **Why:** the batcher's done condition (`ContinuousBatchingEngine.cs` around lines 802-806) is end-of-generation, `MaxNewTokens`, a stop after step, cancellation, or a completed choice. It has no position bound. The only position bound that stops generation is the KV reservation renewal (around lines 678-685), and that runs only when `ReservationRenewer` is set. The ordinary path (`GenerateChunksAsync`, around line 485) sets no renewer, so an ordinary request whose prompt plus output exceeds `MaxSeqLen` keeps decoding. `MaxNewTokens` is not clamped to the window at admission either (only the budget accounting is clamped, around line 1036). The CPU batched decode applies RoPE and the KV append at `positions[n]` with no bound check (`ForwardPass.BatchedIO.cs` around lines 296-312). The comment at `BatchedIO.cs` lines 66-72 says those accesses are unchecked and that overrunning corrupts memory. The single-token checks are in `ForwardCore` only, not in the batched path.
- **Example:** a 4000-token prompt in a 4096-token context with `max_tokens` 1000 decodes positions up to about 5000. A client can send that today.
- **Off-by-one, which the fix must respect:** the decode loop carries one sampled token whose KV is written on the next step. Entering a step at position P writes KV at P, so P must be below `MaxSeqLen`. The token produced at P is materialised at P+1 on the following step, so `P + 2 <= MaxSeqLen` is needed for it to be stored. The reservation renewer already encodes this (`Position + 2`). A token sampled beyond that must be discarded before it is logged or emitted, by the same `StopAfterStep` path the renewer uses.
- **Next step:** add the position rule to the decode loop for every sequence (not only renewers), so a sequence stops, with finish reason `length`, when `Position + 2 > MaxSeqLen`, and never runs a decode step at a position at or beyond `MaxSeqLen`. Handle a prompt that fills the window exactly (it must still produce its first token, which needs no KV write) so that the A28 test keeps passing.

## Rules

1. **Order.** Take items in this order.
2. **A stalled item** gets its blocker written down, in its plan and in [1-correctness/bugstofix.md](1-correctness/bugstofix.md) when it is a bug. Then the next item starts.
