# Implementation Plan — Plan 014: Token Generation Lifecycle Listener (`OnTokenGenerated`)

## Objective

Add a lightweight token-generation observation mechanism to `IInferenceSession` so hosts such as OpenTail can observe committed generated tokens without wrapping or modifying the normal `GenerateAsync()` streaming pipeline.

Example:

```csharp
session.OnTokenGenerated += (token, text) =>
{
    Console.Write(text);
};
```

The feature is intended for:

- UI updates;
- lightweight telemetry;
- token logging;
- debugging;
- latency instrumentation;
- host-side activity monitoring.

It must remain an **observation API**, not become another generation/streaming mechanism.

---

# 1. Public API

Add an event to `IInferenceSession`.

Preferred shape:

```csharp
event Action<int, string>? OnTokenGenerated;
```

Where:

- `int token` = committed token ID;
- `string text` = decoded text corresponding to that committed token.

If Stingray's existing public API has a more appropriate token/result DTO, the coding agent may use that instead.

For example, if a suitable existing type exists:

```csharp
event Action<GeneratedToken>? OnTokenGenerated;
```

is preferable to creating a redundant new type.

**Do not introduce a large observer hierarchy.**

---

# 2. Event Semantics

The most important invariant is:

> `OnTokenGenerated` fires only when a token has been successfully committed to the session.

It must NOT fire for:

- speculative draft tokens;
- rejected speculative tokens;
- rolled-back tokens;
- failed generation;
- tokens generated by a branch that is later discarded.

Example:

```text
Draft:
101 102 103 104

Verification:
101 accepted
102 accepted
103 rejected
104 rejected

Events:
101
102
```

Never:

```text
101
102
103
104
```

This keeps the listener consistent with Stingray's transactional generation model.

---

# 3. Event Ordering

The callback should occur **after the token has become part of the authoritative session state**, but as close to the commit point as practical.

Conceptually:

```text
model inference
      ↓
sampling
      ↓
token selected
      ↓
transaction / validation
      ↓
COMMIT
      ↓
OnTokenGenerated
      ↓
continue generation
```

This means a listener can safely regard the event as:

> "This token is now part of the session."

Do not fire the event before commit.

---

# 4. Streaming Relationship

`OnTokenGenerated` is deliberately complementary to `GenerateAsync()`.

Existing code:

```csharp
await foreach (var chunk in session.GenerateAsync(...))
{
    Console.Write(chunk.Text);
}
```

continues to work unchanged.

The new API allows:

```csharp
session.OnTokenGenerated += HandleToken;

await foreach (var chunk in session.GenerateAsync(...))
{
    // Existing processing.
}
```

The listener should not replace the streaming API.

---

# 5. Do Not Duplicate Generation

Do NOT implement the event by internally subscribing to or consuming the session's own `GenerateAsync()` stream.

The event must originate at the **actual token commit point inside the inference pipeline**.

Bad architecture:

```text
GenerateAsync()
    ↓
internal stream
    ├── caller
    └── event adapter
```

Preferred:

```text
Inference
    ↓
commit token
    ├── GenerateAsync stream
    └── OnTokenGenerated
```

This avoids duplicate buffering and preserves correct transactional semantics.

---

# 6. Token Text

The callback should provide decoded text using Stingray's existing tokenizer/decoder.

Example:

```text
Token ID: 1234
Decoded text: "hello"
```

Do not make hosts perform their own token-ID → text conversion.

Reuse the existing tokenizer.

If the tokenizer's streaming decoder has special handling for:

- byte-pair fragments;
- UTF-8 boundaries;
- multi-byte characters;

the event must follow those existing semantics.

Do not implement a second decoder.

---

# 7. Text Is Best-Effort Representation

The token ID is authoritative.

The `text` value is the human-readable decoded representation.

This distinction matters because token boundaries do not necessarily correspond to complete words or Unicode characters.

For example:

```text
Token 1 → "hel"
Token 2 → "lo"
```

Listeners must be prepared to receive fragments.

Document this clearly.

---

# 8. Unicode / Streaming Safety

Do not assume every individual token produces a complete Unicode character.

If Stingray's tokenizer already has an incremental text decoder, reuse it.

Potentially:

```text
token A → partial UTF-8 sequence
token B → completes character
```

The event's text representation should follow the existing tokenizer's established decoding behaviour.

Do not introduce custom Unicode reconstruction solely for this feature.

---

# 9. Listener Exceptions

This is a critical design decision.

A monitoring callback must **never corrupt or abort inference simply because host code failed**.

Recommended behaviour:

```text
token committed
      ↓
invoke listener
      ↓
listener throws
      ↓
swallow/isolate exception
      ↓
inference continues
```

Do NOT allow:

```text
listener exception
      ↓
generation rollback
```

The inference state is already committed.

A listener is observational infrastructure.

If Stingray has an existing logging/error-reporting mechanism, optionally report listener exceptions there.

Do not introduce a new logging framework.

---

# 10. Listener Invocation Cost

The callback sits on the generation hot path.

Therefore:

- no locks if avoidable;
- no allocations beyond what is already required;
- no task creation;
- no `async void`;
- no blocking;
- no waiting for listeners.

The event should be synchronous:

```csharp
Action<int, string>
```

and listeners are expected to perform lightweight work.

If a host wants asynchronous processing, it can enqueue the event itself:

```csharp
session.OnTokenGenerated += (token, text) =>
{
    queue.Writer.TryWrite((token, text));
};
```

Do not turn Stingray into an event-dispatching framework.

---

# 11. No Listener Fast-Path Overhead

When there are no subscribers, the event path should be extremely cheap.

Conceptually:

```csharp
var handler = OnTokenGenerated;

if (handler is not null)
{
    handler(tokenId, text);
}
```

Do not allocate event payload objects when there are no listeners.

The normal case for many production sessions may be:

```text
OnTokenGenerated == null
```

and should remain effectively free.

---

# 12. Multiple Listeners

Normal .NET event semantics should be used.

For example:

```csharp
session.OnTokenGenerated += MetricsHandler;
session.OnTokenGenerated += UiHandler;
session.OnTokenGenerated += DebugHandler;
```

Each listener observes the same committed token.

One listener failing must not prevent the others from being invoked if practical.

If custom invocation is required to isolate exceptions, implement it carefully.

The coding agent should follow existing project event conventions.

---

# 13. Subscription Lifetime

Listeners are owned by the host.

Normal event unsubscription applies:

```csharp
session.OnTokenGenerated -= Handler;
```

The session should not attempt to manage listener lifetimes automatically.

Hosts must unsubscribe long-lived handlers when appropriate to avoid retaining host objects unnecessarily.

Document this briefly.

---

# 14. Session Forking

Forked sessions must have independent listener sets.

For example:

```text
Parent
    OnTokenGenerated → Handler A

Fork
    Child
```

The child must **not automatically inherit** the parent's event subscribers unless that behaviour is already established by Stingray's session architecture.

Recommended:

```text
Parent handlers → Parent only
Child handlers  → Child only
```

This prevents surprising cross-branch telemetry.

Example:

```text
Parent generates → Parent event
Child generates  → Child event
```

No duplicate notifications.

---

# 15. Suspension / Resume

Suspension must not destroy or serialize event subscriptions.

Subscriptions are host/runtime state, not inference state.

Conceptually:

```text
session
  ↓
subscribe
  ↓
suspend
  ↓
resume
  ↓
same listener remains attached
```

If Stingray's existing session persistence creates a new runtime object during resume, document the appropriate host responsibility rather than serializing delegates.

**Never serialize delegates into `FileSessionStore`.**

---

# 16. Tool Calls

Tool-call outputs and tool results should follow normal session semantics.

The event should fire for **model-generated tokens**.

It should NOT fire for:

- tool-generated text;
- tool results injected into the context;
- host-generated messages.

For example:

```text
Model → "search_web"
```

fires token events.

Then:

```text
Tool → {"results":[...]}
```

does not.

Then model continuation generates:

```text
"The answer is..."
```

and those model tokens fire normally.

---

# 17. Constrained Choice Integration

`AllowedChoices` from Plan 013 must work naturally.

Only tokens actually committed by the constrained sampler should generate events.

For example:

```text
AllowedChoices = ["APPROVED", "REJECTED"]
```

If the model generates:

```text
APPROVED
```

listeners receive those committed token fragments.

Illegal candidate tokens never produce events.

---

# 18. Speculative Decoding Integration

This requires an explicit test.

For:

```text
Draft:
A B C D

Verification:
A accepted
B accepted
C rejected
D rejected
```

events must be:

```text
A
B
```

not:

```text
A
B
C
D
```

If speculative decoding has a batch commit operation, invoke the event after each successfully committed token or after the committed batch, depending on the existing architecture.

The externally visible ordering must still be token order.

---

# 19. Prompt Lookup Speculation

Plan 014/PLD must follow the same rule.

Prompt Lookup candidate tokens are speculative until accepted.

Therefore:

```text
PLD candidate
    ↓
verification
    ↓
accepted
    ↓
OnTokenGenerated
```

Rejected candidates must never trigger the callback.

---

# 20. Metrics Integration

`ISessionMetrics` should remain independently usable.

Do not implement metrics by subscribing internally to `OnTokenGenerated`.

Metrics should continue to be updated at the authoritative engine commit point.

Otherwise an application could accidentally interfere with core metrics simply by manipulating listeners.

The architecture should conceptually be:

```text
              ┌── GenerateAsync
commit token ─┼── OnTokenGenerated
              └── SessionMetrics
```

rather than:

```text
commit token
      ↓
OnTokenGenerated
      ↓
Metrics
```

This preserves a clean separation between core state and observation.

---

# 21. Cancellation and Errors

If a token has not been committed:

```text
no event
```

If a token has been committed and cancellation occurs immediately afterwards:

```text
event already fired
```

This is correct because the event represents committed session state, not successful completion of the entire generation operation.

Example:

```text
Token 42
  ↓
commit
  ↓
OnTokenGenerated(42)
  ↓
Cancellation
```

Token 42 remains part of the session.

Attach multiple listeners and verify all observe the same committed tokens.

# 23. Performance Test / Sanity Check

Because the event is on the token-generation path, include a lightweight performance sanity test or benchmark if the existing project already has benchmark infrastructure.

Compare:

```text
No listener
```

against:

```text
One no-op listener
```

The feature should introduce negligible overhead relative to model inference.

Do not build a new benchmark framework just for this.

---

# 24. Non-Goals

Do NOT implement:

- an observer framework;
- event buses;
- asynchronous event dispatch;
- OpenTelemetry;
- Prometheus;
- logging infrastructure;
- token history storage;
- replay;
- event persistence;
- network callbacks;
- tool execution;
- agent orchestration.

This is simply:

> **A lightweight notification when a model token becomes committed session state.**

---

# 25. Definition of Done

Plan 014 is complete when:

1. `IInferenceSession.OnTokenGenerated` exists.
2. The callback exposes token ID and decoded text, or an equivalent existing Stingray token type.
3. The event fires only for committed tokens.
4. Rejected speculative tokens never trigger it.
5. Rolled-back tokens never trigger it.
6. Token ordering is correct.
7. Existing tokenizer decoding is reused.
8. Listener exceptions cannot corrupt inference.
9. Multiple listeners work correctly.
10. No-listener overhead is negligible.
11. Forked sessions do not unexpectedly share listeners.
12. Suspension/resumption has defined listener semantics.
13. Tool results do not produce model-token events.
14. Constrained-choice generation works correctly.
15. PLD/speculative decoding cannot bypass the commit rule.
16. Streaming `GenerateAsync()` remains completely unchanged.
17. `ISessionMetrics` does not depend on the event.
18. No observer/event framework is introduced.
19. All new tests pass.
20. Full Stingray test suite passes.
21. Release build passes.

---

## Architectural Principle

The key rule is:

> **`OnTokenGenerated` is an observation of committed inference state, not part of the inference state machine.**

The coding agent is encouraged to use a better existing abstraction if Stingray already has one, but should avoid adding unnecessary infrastructure.

The ideal implementation is genuinely tiny:

```text
                    ┌── GenerateAsync()
                    │
committed token ────┼── OnTokenGenerated
                    │
                    └── Metrics
```

The event should sit at the same authoritative commit boundary that already governs `GeneratedTokens`, speculative acceptance, rollback, and session state.

That gives OpenTail a clean "tap" into generation without turning Stingray into an agent framework.
