Rotation application, rotate_pairs (ops.cpp:5933-5950) called for VISION mode as (ops.cpp:6078-6080):

template<typename T>
static void rotate_pairs(int64_t n, int64_t n_offset, const float* cache, const T* src, T* dst, int scale=2) {
  for (int64_t i0 = 0; i0 < n; i0 += 2) {
    const int64_t ic = i0/scale;           // ic = i0/2 ∈ [0, n/2) = [0, d_head/2)
    const float cos_theta = cache[i0+0], sin_theta = cache[i0+1];
    const T* src_ = src + ic;  T* dst_ = dst + ic;
    float x0 = f32(src_[0]), x1 = f32(src_[n_offset]);
    dst_[0]        = f32_to_T(x0*cos_theta - x1*sin_theta);
    dst_[n_offset] = f32_to_T(x0*sin_theta + x1*cos_theta);
  }
}
This is NEOX-style split-half pairing (channel ic paired with ic + n_offset), not interleaved-adjacent NORM style (that's only for GGML_ROPE_TYPE_NORMAL, rotate_pairs<T>(n_dims, 1, ..., scale=1), ops.cpp:6070-6072). Also note if (!is_vision) { ...fill remaining channels... } (ops.cpp:6085-6094) is skippedfor VISION — every channel of d_head gets overwritten by the rotation (no passthrough tail), since ic covers [0,d_head/2) writing both dst[ic] and dst[ic+d_head/2].

1c. Net effect — exact formula for GLM4V

Split the head dim into 4 contiguous quarters of size d_head/4: Q0=[0,H/4) Q1=[H/4,H/2) Q2=[H/2,3H/4) Q3=[3H/4,H) (H=d_head). Let k ∈ [0,H/4) be thewithin-quarter index, theta_scale = rope_theta^(-4/H), pos_row = positions[i2] (stream 0), pos_col = positions[i2+n_patches] (stream 1):

inv_freq(k) = theta_scale^k = rope_theta^(-4k/H)
theta_row(k) = pos_row * inv_freq(k)
theta_col(k) = pos_col * inv_freq(k)
cos/sin computed as cos(theta)*attn_factor, sin(theta)*attn_factor   (attn_factor=1)

for k in [0, H/4):
    (Q0[k], Q2[k])  -> rotated by (cos(theta_row(k)), sin(theta_row(k)))
        out Q0[k] = Q0[k]*cos - Q2[k]*sin
        out Q2[k] = Q0[k]*sin + Q2[k]*cos
    (Q1[k], Q3[k])  -> rotated by (cos(theta_col(k)), sin(theta_col(k)))
        out Q1[k] = Q1[k]*cos - Q3[k]*sin
        out Q3[k] = Q1[k]*sin + Q3[k]*cos
i.e. the classic Qwen2VL-style vision-rope pattern [h_freq, w_freq, h_freq, w_freq] (duplicated concat + rotate-half), applied to the entire head dim — this independently matches the well-known open-source Qwen2VL vision-rope semantics, confirming the trace.

2. Dual-conv patch-embed reshape — exact index trace

ggml_conv_2d output convention (ggml/src/ggml.c:4653-4680, ne[] = fastest-first):
// a (kernel): ne=[KW,KH,IC,OC]   b (input): ne=[IW,IH,IC,N]   result: ne=[OW,OH,OC,N]
ggml_permute(ctx,a,axis0,axis1,axis2,axis3) (ggml.c:3815-3855): old axis i moves to new position axis_i (new_ne[axis_i] = old_ne[i]) — confirmed bysource.

ggml_cont_4d/ggml_cont_3d (ggml.c:3607-3623) materializes a numpy-style reshape of the source's current logical shape (walking it via strides in row-major nested-loop order i3,i2,i1,i0 with i0 fastest, per ggml_compute_forward_dup_bytes, ggml-cpu/ops.cpp:372-410) into a new contiguous tensor of the targetne. This is genuinely numpy.reshape semantics on the permuted view's logical shape, not a physical-memory reinterpretation.

Trace (glm4v.cpp:12,24-37), C=n_embd, W=n_patches_x, H=n_patches_y, B=1:

1. inp = conv2d(patch_embeddings_0, inp_raw); inp_1 = conv2d(patch_embeddings_1, inp_raw); inp = inp + inp_1 — both dual convs are summed elementwise into the same n_embd channels before any reshuffling. (Channel count/identity is untouched by everything that follows — see origin note below.) Post-add inp:ne=[W,H,C,B].
2. ggml_permute(inp, 1,2,0,3) → ne=[C,W,H,B] (comment [w,h,c,b]→[c,w,h,b] confirmed).
3. ggml_cont_4d(→[2C, W/2, H, B]): solving flat_src(c,w,h)=h·W·C+w·C+c against flat_dst(c2,w2,h2)=h2·W·C+w2·2C+c2 gives:
h2 = h
w2 = w // 2
c2 = (w % 2)*C + c
4. ggml_reshape_4d(→[2C, W/2, 2, H/2]) (pure reinterpretation, contiguous): decomposes h = 2·q + p (p=h%2, q=h//2), giving indices (c2, w2, p, q).
5. ggml_permute(0,2,1,3) → logical ne=[2C, 2, W/2, H/2], axes (c2, p, w2, q).
6. ggml_cont_3d(→[C, W·H, B]): solving flat_src = ((q·(W/2)+w2)·2+p)·2C + c2 against flat_dst = t·C + c gives:
t = 2M + (c2 // C)      where M = (q·(W/2)+w2)·2 + p
c = c2 % C
6. Substituting c2 = (w%2)·C + c_orig (from step 3): c2 // C = w%2, c2 % C = c_orig — so the final channel c equals the original summed-conv channelc_orig unchanged. And:
t = 2·(h//2)·W + 4·(w//2) + 2·(h%2) + (w%2)

Verified numerically (W=H=4): this produces token order t=0..15 mapping to (h,w):(0,0)(0,1)(1,0)(1,1),(0,2)(0,3)(1,2)(1,3),(2,0)(2,1)(3,0)(3,1),(2,2)(2,3)(3,2)(3,3) — a 2×2-block raster reorder: block_row=h//2 outer, block_col=w//2 next, then within-block (sub_row=h%2, sub_col=w%2) with sub_row outer / sub_col inner. This is exactly the token order the positions fill loop in §1eproduces (dy outer, dx inner, block stride = n_merge=2).

Answer to your channel question: it's not a channel split at all — the two conv kernels' outputs are already summed into one n_embd-wide tensor before this reshape runs; the entire permute/reshape sequence's only job is spatial patch reordering (raster → 2×2-block-raster), not channel manipulation.Channel c in the final [n_embd, n_patches, 1] output equals the channel of the pre-summed conv output at the corresponding (h,w).

4c. Fused vs separate QKV — confirmed FUSED for GLM4V

There is no GLM4V-specific branch in the per-block tensor loader (clip.cpp:2071-2151) — it's fully generic, always attempting both layer.qkv_w/qkv_b and layer.q_w/k_w/v_w optionally. Which one is actually present in the GGUF is determined by the converter/original checkpoint. Tracing the conversion path:

- GLM4V's vision converter (conversion/qwen3vl.py:225-245, class Glm4VVisionModel(Qwen3VLVisionModel)) does not override or split attention-QKV naming; it passes tensor names through to the base MmprojModel.modify_tensors.
- gguf-py/gguf/tensor_mapping.py:1511-1519 (MODEL_TENSOR.V_ENC_ATTN_QKV) lists "visual.blocks.{bid}.attn.qkv" tagged # qwen3vl (no separate GLM4V splitlogic exists anywhere in the conversion scripts) — the fused HF qkv Linear name is what GLM4V's actual checkpoint uses (same as Qwen3VL), mapping straight to TN_ATTN_QKV.
- By contrast, the separate TN_ATTN_Q/K/V mapping entries (tensor_mapping.py:1532,1558,1584, tagged # qwen2vl, generated) are produced only by the legacy Qwen2VL converter path (conversion/qwenvl.py), which is a different, unrelated converter not used for GLM4V.

Conclusion: GLM4V uses fused QKV (layer.qkv_w/layer.qkv_b, GGUF tensor v.blk.N.attn_qkv.{weight,bias}), split at graph-build time via ggml_view_4d(clip.cpp:381-405):

    // Q at offset 0, K at offset n_head*d_head, V at offset 2*n_head*d_head

One item I could not fully confirm from llama.cpp source alone: whether the per-block qkv_b bias tensor is actually present in real GLM4V GGUFs (i.e.whether the original HF qkv nn.Linear has bias=True). Concretely, for real GLM4V params (d_head head dim, n_dims=d_head/2, quarter size Q=d_head/4), the head-dim splits into 4 contiguous quarters [0,Q) [Q,2Q) [2Q,3Q) [3Q,4Q):

This is because the original HF module is a single Conv3d with temporal kernel size 2 (visual.patch_embed.proj,weight shape [OC,IC,kt=2,KH,KW]), which the converter splits into two Conv2d kernels along the temporal axis (conversion/qwen3vl.py:128-141):

Conv3d output = Σ over kt of conv2d_kt(frame_kt); for a still image the two temporal frames are the same image, so conv0(img)+conv1(img) reproduces the Conv3d result. So the permute/reshape block's only job is reordering PATCH POSITIONS, not channels. Channel index is passed through unchanged.

Confirmed ggml semantics used:
- ggml_conv_2d (ggml.c:4653-4680): comment convention is "numpy order" (reversed of ne[]): a:[OC,IC,KH,KW] → ne=[KW,KH,IC,OC]; b:[N,IC,IH,IW] → ne=[IW,IH,IC,N]; result:[N,OC,OH,OW] → ne=[OW,OH,OC,N]. So inp after conv+add has ne = [n_patches_x, n_patches_y, n_embd, 1] (W,H,C,B).
- ggml_permute(ctx,a,axis0,axis1,axis2,axis3) (ggml.c:3815-3855): new_ne[axis_i] = old_ne[i] — old axis i moves to new position axis_i.
- ggml_cont_*d/reshape (backed by ggml_compute_forward_dup_bytes, ops.cpp:326-410, contiguous-dst branch at ops.cpp:372-409): walks the source's ownlogical shape (post-permute, via strides) in nested loops i03,i02,i01,i00 (i00 innermost/fastest) and writes sequentially into the destination's flat contiguous buffer, i.e. exactly numpy reshape semantics applied to the permuted logical shape, ne0-fastest.

Trace (C=n_embd, W=n_patches_x, H=n_patches_y, B=1):

Step 1 — permute(1,2,0,3): [W,H,C,B] → [C,W,H,B] (logical view; new_ne[1]=old W, new_ne[2]=old H, new_ne[0]=old C).

Step 2 — cont_4d(2C, W/2, H, B): flattening (c,w,h,b) (ne0=c fastest) and re-splitting into (c2,w2,h2,b) gives:
h2 = h
w2 = w // 2
c2 = (w % 2)*C + c

Step 3 — reshape_4d(2C, W/2, 2, B*(H/2)) on axes (c2,w2,p,q):
p = h % 2
q = h // 2
(c2, w2 unchanged.)

Step 4 — permute(0,2,1,3): [c2,p,w2,q] → [c2, w2, p...  — concretely new logical shape becomes ne=[2C, 2, W/2, B*H/2], axes (c2, p, w2, q).

Step 5 — cont_3d(C, W*H, B): flatten source axes (q,w2,p,c2) (q slowest .. c2 fastest) into target (b,t,c):
c = c2 % C                         // = original conv-output channel, unchanged
t = 2*[(q*(W/2)+w2)*2 + p] + (c2 // C)
  = 2*q*W + 4*w2 + 2*p + (w % 2)
Substituting back q=h//2, p=h%2, w2=w//2:
t(h,w) = 2*(h//2)*W + 4*(w//2) + 2*(h%2) + (w%2)

Result (verified against the pos-fill loop, exact match): output token index t ∈ [0, n_patches) corresponds to spatial patch (h,w) via 2×2-block reordering:
block_row = h // 2,  block_col = w // 2         (raster order over blocks: row-major, block_row outer / block_col inner)
sub_row   = h % 2,   sub_col   = w % 2           (raster order within block: sub_row outer / sub_col inner)
t = (block_row * (W/2) + block_col) * 4 + (sub_row * 2 + sub_col)
Channel index is unchanged (c = c2 % C, i.e. simply the summed-conv output channel, n_embd-wide). This exactly matches the positions[] fill loop in item 1 (y+=merge_ratio(=2), x+=merge_ratio(=2), then dy∈{0,1} outer, dx∈{0,1} inner) — confirming the reorder exists specifically so that RoPE position streams and the later patch-merger's "consume 4 consecutive tokens" grouping line up with spatial 2×2 blocks. This derivation assumed n_merge==2 (GLM4V'sactual/default value); the reshape's /2 and 2 literals are hardcoded to exactly 2, so it is not generic over n_merge.

The same reshape (steps identical) is applied to learned_pos_embd at glm4v.cpp:51-60 for identical reasons (align interpolated position embeddings with the same token ordering).

cur = ggml_conv_2d(ctx0, model.mm_patch_merger_w, cur, n_merge, n_merge, 0,0,1,1);
cur = ggml_reshape_2d(ctx0, cur, cur->ne[2], n_token_out);        // [n_embd_out, n_token_out]
cur = ggml_add(ctx0, cur, model.mm_patch_merger_b);

Input cur at this point has ne=[n_embd, n_patches, 1], tokens already in the item-2 2×2-block order, i.e. consecutive runs of n_merge²=4 tokens are exactly one spatial 2×2 merge-block (no extra shuffling needed — reshape_4d(n_embd, n_merge, n_merge, n_token_out) on axes (c,a,b,tok) gives t =tok*n_merge² + b*n_merge + a, i.e. local index a=fastest=sub_col≈dx, b=sub_row≈dy, matching item 2's local ordering exactly).

After permute(2,0,1,3) + cont: logical/physical shape ne=[n_merge(a), n_merge(b), n_embd(c), n_token_out(tok)]. Feeding this as ggml_conv_2d's input b, per the comment convention b:[N,IC,IH,IW]→ne=[IW,IH,IC,N]: IW=n_merge(a=dx-axis), IH=n_merge(b=dy-axis), IC=n_embd, N=n_token_out — each merged outputtoken is treated as its own independent "image" in the conv batch dimension. Kernel a:[OC,IC,KH,KW]→ne=[KW,KH,IC,OC] = model.mm_patch_merger_w with ne=[n_merge, n_merge, n_embd, n_embd_out] (GGUF/HF-style shape reversed: [n_embd_out, n_embd, n_merge, n_merge], i.e. exactly the naturalnn.Conv2d(n_embd, n_embd_out, kernel_size=n_merge, stride=n_merge) weight layout — HF source is visual.downsample per tensor_mapping.py:1850, confirming it's a real Conv2d, not a linear-reshape trick).

Since stride==kernel==n_merge and padding 0, OH=OW=1; ggml_conv_2d result ne=[1,1,OC,N], and the final reshape_2d(cur->ne[2]=OC, n_token_out) triviallysqueezes the two size-1 dims (flat order is preserved bit-for-bit). Confirmed simplification is exactly correct:
out[oc, tok] = bias[oc] + Σ_{ky=0}^{M-1} Σ_{kx=0}^{M-1} Σ_{ic=0}^{n_embd-1}
                   W[oc][ic][ky][kx] * vit_out[ic, tok*M*M + ky*M + kx]
where M=n_merge, W indexed in numpy/GGUF order [oc][ic][ky][kx] (ky↔input's IH/b-axis/sub_row/dy, kx↔input's IW/a-axis/sub_col/dx), and vit_out[ic, t] isthe ViT output in the item-2 token order (so no separate un-shuffle step is needed in the C# port — just walk vit_out sequentially in groups of 4).

Per-block attention (clip.cpp:2076-2095, fully generic loader, no GLM4V-specific branch): both fused (TN_ATTN_QKV="%s.blk.%d.attn_qkv.%s") and separate(TN_ATTN_Q/K/V) are attempted optionally; which one is actually populated is determined by the GGUF file, which in turn is determined by the converter. Tracing the converter: GLM4V's vision tower is registered as Glm4VVisionModel(Qwen3VLVisionModel) in conversion/qwen3vl.py:225-245, and does not overrideattention-tensor naming — it falls through to the base MmprojModel.modify_tensors, so the raw HF tensor name visual.blocks.{bid}.attn.qkv.{weight,bias} passes straight through and matches tensor_mapping.py:1511-1519's V_ENC_ATTN_QKV pattern "visual.blocks.{bid}.attn.qkv" (tagged for qwen3vl, and byinheritance for GLM4V too — GLM4V is not listed among the entries in the V_ENC_ATTN_Q/K/V split-tensor group, which are explicitly tagged # qwen2vl, generated, i.e. produced only by the separate legacy qwen2vl converter). Conclusion: standard GLM4V uses a fused attn_qkv.weight/.bias tensor per block(layer.qkv_w/layer.qkv_b), not separate Q/K/V. I could not find an explicit assertion on bias presence in clip.cpp; biases are loaded optionally either way (get_tensor(...,false)), so bias presence is determined purely by what's in the actual GGUF — worth confirming against a real GLM4V GGUF's tensor list before assuming bias exists, though Qwen-family vision qkv projections conventionally do have bias.

TN_ATTN_Q_NORM/TN_ATTN_K_NORM = "%s.blk.%d.attn_{q,k}_norm.%s" are optional and, per tensor_mapping.py:1543,1569 ("visual.blocks.{bid}.attn.q_norm" # GLM-OCR), only present for the GLM-OCR variant — the same variant that lacks position_embeddings. One documentation caveat

The header comment example for GGML_ROPE_TYPE_VISION in ggml.h:1862-1866 ("sections=[y=4,x=4,0,0], head=8, n_dims=4 → [yyyyxxxx]") does not numerically reproduce when I mechanically execute the real ggml_mrope_cache_init/rotate_pairs code with those literal parameters — sections in that toy example don'tsatisfy the code's own invariant. I did not rely on that comment; the formulas above come from directly tracing the actual ops.cpp source with GLM4V's real parameter shapes (sections={d_head/4}×4, n_dims=d_head/2), cross-checked three independent ways (sector arithmetic, rotate_pairs bounds, andconsistency with the positions[] fill loop / patch-merger token grouping), so I'm confident in it — just flagging that the header comment itself shouldn't be trusted as a cross-check.
