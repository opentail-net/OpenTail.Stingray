## Branch map (llama.cpp → this engine)

| llama.cpp branch | Engine | Status |
|---|---|---|
| Single-sublayer dispatch: MoE layer = FFN-only block (kv 0, ff > 0) | `HybridFfnOnlyLayer` (existing); the FFN-only branch of `ForwardPass.Decode.cs` now calls `MoeFfn` when `IsMoeLayer(layer)`, else `DenseFfn` | **changed** |
| Router: `router_logits = ffn_gate_inp · cur` on the full-width input; sigmoid gating with `exp_probs_b` selection bias | `MoeFfn` router (existing); `ExpertGatingFunc = 2` set in the descriptor semantics | reused |
| Experts: `build_moe_ffn(inp_latent, ..., gate = nullptr, ..., RELU_SQR)`: up → relu² → down, no gate | `MoeFfn` sequential loop, non-gated branch (`gatedExperts` = gate tensor present) | **new** |
| Latent: `inp_latent = ffn_latent_down · cur`; experts run on it; `moe_out = ffn_latent_up · moe_out` | `_wLatentDown` / `_wLatentUp` (new), latent buffers `_latentIn` / `_latentOut`, applied inside `MoeFfn` when `_latentDim > 0` | **new** (used only if the tensors exist) |
| Shared expert: `build_ffn(inp_emb, up_shexp, relu², PAR)` with no gate | `MoeFfn` shared branch, non-gated when `ffn_gate_shexp` is absent | **new** |
| Output: `cur = moe_out + ffn_shexp` | `MoeFfn` step 4 (unchanged) | reused |
| No RoPE on attention blocks; no embedding scale | `NoRopeLayerStep = 1` (as `nemotron_h`) | reused |
| Batched prefill | `_perTokenTrunkOnly` set for hybrid MoE layers, so prefill runs per token through `MoeFfn` | **new** |

Tensor loading: `TryResolveTensor` returns an empty reference for absent tensors, so a missing gate (`ffn_gate_exps`, `ffn_gate_shexp`) selects the non-gated path instead of failing the load.

The FFN and Mamba-2 shares are stable across runs. The largest target is the FFN (MoE experts, routed and shared); the Mamba-2 mixer is second. No change to the engine's numerics or speed has been made yet. The perf pass needs a before-and-after series on a specific change, which is the next step. Checked 2026-11-27 before choosing one: the routed and shared expert matvecs are already row-parallel (`SimdKernels.MatVecQ4_0` parallelises at `rows >= MinRowsForParallel` = 64, and the expert rows are 1856 and 2688), so splitting experts across threads is not the gap. Non-gated experts (ReLU²) skip the folded fast path and run the sequential loop in `ForwardPass.Moe.cs`. Weight bytes per non-gated MoE layer per token, Q4_0 at 0.5625 B/weight: six routed experts (up and down, 2.81 MB each) plus the shared expert (up and down, 5.61 MB each), about 45 MB. The FFN share of the median token is about 41 ms (47.8% of 84.97 ms). Measured 2026-11-27 (scratch programs in the session scratchpad, not in the repo). MoE layers: 23 of 52, from the full GGUF header (`feed_forward_length`), so about 1.03 GB of expert weights per token. Sequential read probe, 1 GiB, all 16 logical CPUs: median 39.8 GB/s (best 40.4). The FFN achieves about 25 GB/s (1.03 GB over 40.6 ms). An isolated run of the same expert matvecs in the engine's access pattern, using the engine's row-parallel `MatVecQ4_0`: median 45.6 ms/token (range 44.4 to 200.4, one outlier), 22.6 GB/s. So the loss is in the Q4_0 expert kernel, not in the expert loop around it. Single-thread comparison on the same shapes: float activations (`DotQ4_0`) 214 ms/token, Q8_0 activations (`DotQ4_0_Q8_0`) 194 ms/token, a 1.11x speedup. Q8 changes the matvec output by a relative L2 of 3.0e-3 per projection, a numerics change for little gain, so it is not recommended on these numbers. Next: find why the float kernel reaches about 57% of the sequential read rate (row access pattern, per-row block loop, chunking), and measure any candidate in the isolated benchmark before touching the engine. Dispatch overhead, measured 2026-11-27 on the same 45 MB per sweep: 16 per-expert `MatVecQ4_0` calls, median 25.8 GB/s (range 9.7 to 26.8); one batched call over all 16 experts, median 30.4 GB/s (range 28.6 to 31.7). Batching recovers about 18% of the kernel rate, so dispatch overhead is part of the gap, but the batched call still sits well short of the 39.8 GB/s probe. The batched form keeps each row's dot product and the weighted sum order unchanged, so it should not change numerics; the golden check is done: `admit-arch --golden` gives Exact 16/16 on all three recorded cases (default, prompt2 and the long case), with the batched path active. Batched path implemented in `ForwardPass.Moe.cs` (`NonGatedExpertsBatched`, switch `MoeNonGatedBatchedEnabled`). Generated text at temp 0 is identical to the pre-change run. Series, five runs on the batched binary (no profiling, same command as before): decode 12.6 t/s median (12.5 to 12.9), prefill 11.9 t/s median (11.2 to 12.1). Baseline caveat: the pre-change untimed series gave 10.6 t/s decode (4.8 to 10.9, noisy); the profiled series on `22c03fd0` gave 11.8 t/s with profiling overhead. So the gain is about +7% to +19% depending on the baseline. **Settled 2026-11-27 by an interleaved A/B in one process** (switch flipped every 10 decoded tokens, machine state shared, 40 tokens per arm after warm-up): batched 91.50 ms/token (range 87.3 to 98.6), sequential 91.44 ms/token (range 86.8 to 104.7), speedup 0.999x. **There is no measurable gain, so the batched path is removed** (CLAUDE.md rule 7: a change that is not measurably faster is reverted). The earlier 12.6 t/s series was baseline noise. The batched code and its bit-identity test are removed by a forward commit that restores `ForwardPass.Moe.cs` from `58482dff`; the golden checks had passed for the batched path, so the path was correct, just not faster. The dispatch-overhead lead above (18% in the isolated kernel) did not carry into the engine. Next: the isolated kernel's float path is still about 57% of the read rate, but a candidate has to show a gain in the full engine before it is kept. **Two more candidates tested 2026-11-27, neither kept.** (1) Software prefetch of rows 8 or 16 ahead, isolated, same 45 MB sweep: no prefetch 34.2 GB/s, prefetch 8 ahead 32.6, prefetch 16 ahead 31.6 (ranges overlap).
